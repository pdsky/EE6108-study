Topic 2.1 · 数据链路控制 从零学习

把你当成完全没学过的新手 —— 每个概念都配有生活类比、逐步推导公式和完整例题。建议先完整读一遍"图文教程",再用卡片、自测题和计算器巩固。

01 数据链路层在干什么?——邻里之间的"快递小哥"

回忆一下 Topic 1:网络层(IP)负责把数据报从"源头"一路规划路线送到"终点",走的是一整条跨越多个路由器的路径。而数据链路层只管一件事:把数据"安全地送到隔壁那一个相邻节点"——它不关心最终目的地在哪,只负责"这一跳"。

类比:如果网络层是快递公司的"总调度系统"(规划从上海到北京要经过哪些中转站),那数据链路层就是每一段路上具体开车的快递小哥——他只负责把包裹从这一个中转站安全送到下一个相邻的中转站,中途换了车、换了司机(不同链路用不同协议,比如第一段用以太网、中间用帧中继、最后一段用 WiFi),对总路线毫不关心。
几个基础术语
  • 主机、路由器统称节点(nodes);连接相邻节点的信道叫链路(links)
  • 两种链路信道:广播信道(大家共用同一条"频道",如 LAN、无线LAN,谁都能听到)、点对点信道(专线,如 HDLC)
  • 链路层的 PDU 叫帧(frame)——它把网络层传下来的数据报"装进信封"再发出去
数据链路层要负责的四件事
  • 成帧(Framing):给数据报加上头部/尾部,包成一个"帧"
  • 链路接入:大家共用同一条信道时,谁先说话、怎么排队,由 MAC 协议规定,帧头里的 MAC 地址标明"这是谁发的、要给谁"
  • 相邻节点间可靠传输:靠确认(ACK)和重传机制,保证这一跳不出错——常用于容易出错的链路(比如无线),光纤这种低错误率链路则很少用
  • 流量控制与差错控制:本章接下来两大块的主题

IEEE 802 标准把链路层再细分成两个子层:LLC(逻辑链路控制)负责对上层提供统一接口、做流量与差错控制;MAC(介质访问控制)负责实际的组帧/拆帧、地址识别、差错检测。这一整套逻辑最终落地在你电脑里的网卡(NIC)上,是软硬件结合的产物。

  • 数据链路层只管"相邻两节点之间的这一跳",不管全局路径
  • 核心四件事:成帧、链路接入、可靠传输、流量/差错控制

02 流量控制是什么问题?——先从最简单的 Stop-and-Wait 讲起

接收方的"收件箱"(缓冲区)是有限的。如果发送方发得太快,接收方来不及处理,缓冲区就会溢出、数据丢失。流量控制就是想办法让发送方的速度"配合"接收方的处理能力,别把对方压垮。本节先假设网络非常理想——所有帧都能正确送达,不会丢、不会错——先专注理解"节奏"问题,下一节才引入"出错"这个变量。

类比:Stop-and-Wait 就像用对讲机说话——你说完一段话必须说"完毕(over)",然后停下来等对方回一句"收到(roger)",才能继续说下一段。哪怕你还有很多话要说,也必须一段一段来,说完等,等完再说。
这样做的代价:被"晾在一边"的时间

发送方发完一帧后,要经过"帧传过去的时间(tframe)"+"信号跑到对方那儿的时间(tprop)"+"对方回一个 ACK 传回来的时间"才能开始发下一帧。忽略掉 ACK 本身很短的传输时间,一来一回的总时间(记作 TD)是:

TD = 2 × tprop + tframe (2个tprop:一次是数据帧跑过去,一次是ACK跑回来;tframe:把整个帧"推"上链路的时间)

这段时间里,链路真正在"干活"(传输有效数据)的只有 tframe 这一小段,其余时间都在"干等"。于是我们定义一个非常关键的比值:

a = tprop / tframe (传播时延 相对于 帧传输时间 有多长) 链路利用率(效率) U = tframe / TD = tframe / (2·tprop + tframe) = 1 / (1 + 2a)

直觉上看:a 越大(意味着链路很长、或者帧很短很快就发完了),等待 ACK 的时间相对占比就越大,效率 U 就越低。反过来,如果链路很短(a 很小),几乎不用怎么等,效率就接近 1。这就是为什么 Stop-and-Wait 在"长肥管道"(高带宽、长距离,比如卫星链路)上效率极低——例题里 1Gbps + 15ms 传播时延的场景,算出效率只有 0.027%!

更精确一点的模型还会算上节点处理时延 tproc、以及 ACK 帧本身的传输时间(它也占用带宽,只是通常很短):

TD = 2·tprop + 2·tproc + Lf/R + La/R (Lf = 数据帧长度,La = ACK帧长度,R = 信道速率)
  • Stop-and-Wait:发一帧、等 ACK,简单但可能大量时间在"空等"
  • a = tprop/tframe 是理解一切流控效率公式的钥匙
  • U = 1/(1+2a):a 越大,链路利用率越低

03 滑动窗口——与其"一句一等",不如"攒着一起发"

Stop-and-Wait 的毛病很明显:大部分时间都在"傻等"。滑动窗口协议的思路很简单——既然反正要等,不如趁着等 ACK 的这段时间,多发几帧出去,而不是一帧发完就停手。

类比:这就像一个项目经理不再"布置一个任务、等做完汇报了才布置下一个",而是一次性派发编号 1~7 的 7 个任务给下属,下属做完第 3 个时可以回复"1、2、3 都收到确认",经理看到确认后又能立刻再派发新任务补满到 7 个——始终保持"手里有活在跑",而不是干等。
规则
  • 最多允许 W 帧"在途"(已发出但还没确认)
  • 帧按编号发送,编号在 0 到 2^k−1 之间循环(k 位序号字段)
  • ACK 是累积确认:收到 "RR i" 意味着"编号 i−1 及之前的全部帧都已正确收到,现在期待编号 i"
效率取决于窗口 W 够不够"填满"等待时间

还是用参数 a = tprop/tframe。关键在于比较 W 和 2a+1 谁大:

情况一:W ≥ 2a+1(窗口足够大) —— 在"第一帧的 ACK 赶回来"之前,窗口还没被发完,链路一直有数据在传,不会出现空闲 —— U = 1 (100% 利用率!) 情况二:W < 2a+1(窗口不够大) —— 发完 W 帧后,ACK 还没回来,只能干等,链路出现空闲 —— U = W / (2a+1)

其中 a 完整展开是 a = tprop/tframe = Rd/(VL)(R=数据速率,d=链路距离,V=信号传播速度,L=帧长)。可以看到:滑动窗口的效率最高能达到 Stop-and-Wait(相当于 W=1)的 W 倍——这正是"攒着发"带来的收益。

  • 核心思想:与其一帧一等,不如让多帧"同时在路上"
  • W ≥ 2a+1 时效率可达 100%;W 太小时,效率退化为 W/(2a+1)

04 差错控制:出错了怎么办?——ARQ 三兄弟

前两节假设"网络很完美,不会出错"。现实中链路会有噪声、信号衰减,帧可能丢失(压根没到)或者损坏(到了但内容错了)。ARQ(自动重传请求)就是把一条不可靠的链路,通过"检测错误 + 确认/重传"的机制,变成一条可靠的链路。三种主流方案,复杂度和效率依次递增:

① Stop-and-Wait ARQ ——最朴素的版本
类比:还是对讲机模式,只是现在信号可能不好——你说完一段话等对方回复,如果超过一段时间没听到"收到"就重新说一遍(超时重传);如果你收到的那段话本身听不清(帧损坏),直接当没收到处理,让对方超时后自己重说。优点是简单,缺点是效率低,而且一旦出错就要完整再等一轮。典型应用:TFTP(简单文件传输协议)。
② Go-back-N ARQ ——回退重传一整批
类比:项目经理发出编号 1~7 的任务,下属发现第 3 个任务的说明有问题(读不懂,即帧损坏),于是直接拒收第 3 个及其后所有已收到的任务(4、5、6、7 全部作废),让经理"回退"到第 3 个重新派发 3、4、5、6、7 这一整批——哪怕 4、5、6、7 其实内容是对的,也要全部重来一遍,因为接收方图省事,只维护一个"简单期望值",不愿意缓存乱序到达的任务。典型应用:HDLC。
③ Selective-Repeat ARQ ——只补发出问题的那一个
类比:同样是 1~7 号任务,第 3 个出问题时,下属把 4、5、6、7(虽然乱序)先收好放进自己的"暂存柜",只单独要求经理重发第 3 个,补齐后再按顺序整理提交。这样重传的开销最小,但下属需要更聪明的"暂存柜"逻辑(缓冲区+重排序),实现更复杂。典型应用:TCP 使用的是这种思路的变体。
ARQ 的四个基本要素
  • 错误检测(接收方怎么发现帧坏了 —— 见下一节)
  • 正向确认 ACK(收到就告诉对方)
  • 超时重传(等太久没回复就重发)
  • 负向确认 NAK + 重传(明确告诉对方"这个坏了,重发")
出错概率 p 会怎样拖累效率?

用误码率 p(一帧出错的概率)修正之前的效率公式。三种方案的直觉是:重传开销越大的方案,受 p 的影响越严重——Go-back-N 每次出错要重传一整个窗口,受影响最大;Selective-Repeat 只重传出错的那一帧,受影响最小。具体公式可以在"计算器"标签页里直接代入 a、p、W 观察三者差异。

  • S&W ARQ 简单但慢;Go-back-N 效率较高但出错代价大;Selective-Repeat 效率最高但实现最复杂
  • ARQ 把不可靠链路"包装"成可靠链路,靠的就是检测+确认+重传

05 差错检测——接收方怎么知道帧坏了?

ARQ 能重传的前提是接收方得先发现数据错了。三种由浅入深的检测手段:

① 奇偶校验(Parity Check)——最简单的"数数游戏"
类比:发送前先数一下这串比特里"1"的个数,如果是奇数就在末尾补一个 1、凑成偶数(这叫"偶校验");接收方收到后也数一遍 1 的个数,如果不是偶数,就知道传输中出错了。问题是:如果恰好有两位同时翻转(比如两个 0 变 1),1 的总个数还是偶数,校验位就发现不了——所以单一奇偶校验只能检测奇数个比特的错误,大约只能覆盖 50% 的错误模式。想要更强,可以用二维奇偶校验(给每一行、每一列都加校验位),这样能可靠检测 1~3 位错误。
② Internet Checksum ——"对账"的思路
类比:好比记账时把所有收据金额加总,写在最后一栏作为"核对数"。具体做法:把要发送的数据切成若干个 16 位的"字"(word),当成整数全部加起来,再取一个特殊的"补数"作为校验和,一起发出去。接收方收到后把所有字(含校验和)加总,如果结果应该是"全 1",就说明没出错。它的弱点是只关心"总和"、不关心"顺序"——如果有人把几个字的顺序打乱,或者插入/删除几个全零的字,总和完全不变,checksum 根本发现不了。

具体计算:把 L 个 16 位字当整数相加,x = (b0+b1+…+bL-1) mod (2^16−1),校验和 bL = −x mod (2^16−1)。可以在"计算器"标签页里代入课件例题(4位字长的 1000/1010/0000/1001)亲手验证一遍,结果应该是 0011。

③ CRC(循环冗余校验)——目前最强、用得最广的方法
类比:CRC 不只关心"总和",而是把整串数据当成一个很长的"数字"(用多项式表示),双方事先约定好一个"除数"(生成多项式 C(x))。发送方在数据末尾补上一段"余数"位,使得整个"数据+余数"恰好能被这个除数整除——这段余数就叫 FCS(帧校验序列)。接收方拿到整个码字后用同一个除数去除,如果除得尽(余数为 0),就认为没错;除不尽,就说明中途出错了。这跟你小学做除法验算是同一个道理,只是这里的"数字"和"除法"都是在二进制、"模2运算"下进行的(加减法都变成异或 XOR,不用进位借位)。

CRC 之所以强,是因为选对生成多项式后能数学证明它能可靠抓住哪些类型的错误:

  • 性质 P1:只要 C(x) 的项数多于 1 项,就能保证检测出所有单比特错误
  • 性质 P2:C(x) 含有因子 (x+1),就能检测出所有奇数个比特错误
  • 性质 P3:满足特定条件时能检测出所有双比特错误
  • 性质 P4:C(x) 阶数为 k,就能检测出长度 ≤ k 的所有突发错误(连续一串错误)

实际标准里常见的生成多项式包括 CRC-8(用于 ATM、Bisync)、CRC-16、CCITT-16(用于 HDLC)、CCITT-32(用于以太网等 IEEE 802 标准)——阶数越高,能可靠检测的突发错误长度也越长。可以在"计算器"标签页里输入课件例题(数据 1100,生成多项式 x³+x+1 即 1011)看看完整的除法过程与结果。

  • 奇偶校验:简单但弱(漏掉偶数个错误)
  • Checksum:看总和不看顺序,漏掉重排序/全零增删
  • CRC:基于多项式除法,数学上能保证检测特定类型的错误,是实际标准的主流选择

Topic 1 补充例题 · 存储转发(含处理/传播时延)

Host A → Host B,三条 1 Mbps 链路

分组头部 80 字节,每个中间节点处理时延 1 ms,每条链路传播时延 10 ms,排队时延忽略。M = 8000 字节大文件。
a) 整体作为一个大分组发送 (h=640 bit) Tm = L(M+h)/R = 3×(64000+640)/10⁶ = 193.92 ms Ttotal = 2·Tproc + 3·Tprop + Tm = 2×1 + 3×10 + 193.92 = 225.92 ms b) 切成 N=8 个 1000 字节分组 (k=8000 bit, h=640 bit) 单分组传输时间 Tpacket = (k+h)/R = 8.64 ms 第一个分组到达: T1 = L·Tpacket + 3·Tprop + 2·Tproc = 3×8.64 + 30 + 2 = 57.92 ms 其余 N−1 个分组依次到达: T2 = (N−1)·Tpacket = 60.48 ms 总时延 D = T1 + T2 = 118.4 ms
结论:切分为更小分组后总时延从 225.92 ms 降至 118.4 ms — 流水线效应显著。
Topic 2.1 补充例题 1 · Stop-and-Wait 效率

已知效率求帧长

信道速率 R = 4 Kbps,传播时延 tprop = 20 ms,要求 Stop-and-Wait 效率 U = 50%,求帧长 L。
U = tframe / (tframe + 2tprop) 0.5 = tframe / (tframe + 2×20ms) => tframe = 2×tprop = 40 ms L = R × tframe = 4×10³ × 40×10⁻³ = 160 bit(20 字节)
答:帧长应为 160 bit(20 字节)。
Topic 2.1 补充例题 2 · Stop-and-Wait 效率与吞吐量

已知帧长求效率与吞吐量

信道速率 R = 1 Gbps,传播时延 tprop = 15 ms,帧长 1000 字节(8000 bit)。求链路效率与吞吐量(bps)。
tframe = L/R = 8000/10⁹ = 8 µs U = tframe / (2tprop + tframe) = 0.008 / 30.008 ≈ 0.00027 吞吐量 = U × R ≈ 270 kbps
答:效率仅约 0.027%,吞吐量约 270 kbps — 长传播时延严重拖累 Stop-and-Wait 性能。
